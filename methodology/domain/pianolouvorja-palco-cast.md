# Pianolouvorja Palco Cast

> **Metodologia pública** — arquitetura multi-tela e cast para TV. Aplica-se a qualquer stack.

---
Cast de projeção/áudio para TVs via WebSocket próprio — NÃO Chromecast. A TV conecta no sender (desktop/APK). Paridade com `PalcoOrchestrator`/`StageSession` do APK (branch `feature/palco-ws-transport`).

## Arquitetura (aprendida em 25/08)

- **Sender** (Electron main `electron/palco-server.mjs`): HTTP + WS por slot.
- **Slots multi-TV**: slot 0 = 7080/7081 (principal), slot N = `7080+2N`/`7081+2N` (TV 2: 7082/7083...). Cada slot: HTTP/WS/mídia/replay de estado próprios.
- **Protocolo "Palco v2"** (WS JSON): `projection` (text/footer/bg/fontSize px@1080p), `bgPalco`, `audio` (url/positionMs/action play|pause|stop|seek/title/cover), `video`, `timer`, `idle`, `youare`. SEM ping (webOS 4.x não responde).
- **Roteamento por módulo** (`palco-routing.ts`): `mirror` (todas as TVs) ou slot individual — persistido em localStorage. Seletor `PalcoRouteSelect` no header de cada módulo.
- **Áudio**: UMA TV de áudio por vez (igual APK `routesToTv`). Em rota `tv`, o player local fica com `volume=0`, mas continua tocando como CLOCK: `audio.timeupdate` move letras/slides/fila. Nunca pausar o clock local durante reprodução TV, ou áudio e letra divergem. `pause` pausa local + envia `audio.pause`; `play` retoma ambos. Sem rota TV → espelho sincronizado; seek só com desvio perceptível.
- **Bridge** (`palco-bridge.ts`): espelha TODOS os módulos (media/bible/random/timer/countdown/clock) via BroadcastChannel+storage das views de projeção. Owner-based: último módulo ativo é o dono do palco.

## REGRA CRÍTICA: sincronização do receiver em 4 pontos

Qualquer mudança no receiver HTML vai para TODOS:
1. `palco-receiver/webos/index.html` (→ .ipk via `ares-package`)
2. `palco-receiver/tizen/index.html` (→ .wgt via `tizen package -t wgt`; precisa JAVA_HOME)
3. `palco-receiver/androidtv/assets/palco/receiver.html` (asset Flutter — precisa rebuild APK)
4. `piano-desktop/electron/palco/receiver.html` (receiver embutido servido em :7080)

Dessincronização aqui foi a causa de "funciona no browser, não funciona na TV".

## Pitfalls (reais, desta implementação)

- **App empacotado webOS bloqueia `fetch http://` pra LAN** — scan E IP manual falhavam juntos (ambos usavam probeSender/fetch `/status`). Fix: IP manual chama `doConnect()` DIRETO (WS não sofre CORS) + `directTry()` como fallback quando o probe falha com host salvo. WebSocket sempre funciona.
- **Preload expõe `window.louvorja.palco`** (contextBridge), NÃO `window.palco`. PalcoSession tipa o acesso.
- **BG oficial**: `resolveBackgroundImage` devolve `/assets/bg-XX-<hash>.png` (caminho do build) — inacessível pra TV. O server serve em `/bg/:id.png` (varre dist/assets por prefixo); session converte pra URL absoluta `http://ip:7080/bg/...`.
- **Áudio local**: desktop usa `local://media/<tipo>/<arquivo>` (esquema custom do workspace). IPC `palco:serve-path` resolve isso (`./paths.mjs` → `resolveMediaDirectory`) e publica em `/media/`. http(s) do catálogo segue direto (receiver faz proxy).
- **`/proxy?url=`** é obrigatório: receiver roda em origem local e envelopa TODO http através do sender.
- **Versão do receiver DINÂMICA e SEMPRE a do RECEIVER (não a do desktop!)**: cascata `?v=` > `appinfo.json` (webOS E desktop embutido — o palco-server serve `electron/palco/appinfo.json`) > `config.xml` (Tizen) > fallback. **NÃO injetar a versão do package.json do desktop** — usuário corrigiu explicitamente: o browser tem que mostrar a versão do .ipk/receiver instalado (ex.: v0.1.20), nunca a release do PIANO (1.17.5). O `appinfo.json` é o 5º ponto de sincronização do receiver.
- **i18n: inserção por anchor em locale .ts pode cair no BLOCO ERRADO** (chaves `palco.*` entraram dentro de `settings.general` porque o anchor `desktopOnly:` existia nos dois blocos). Sintoma: chave crua `settings.palco.tvs` na UI. Após editar locale, SEMPRE conferir o bloco pai. Arquivos CRLF: sed falha silenciosamente; usar patch tool. **E ANTES DE ADICIONAR chave nova, grep se JÁ EXISTE no bloco** (`tvs` já existia em palco → TS1117 duplicada; caiu 3x na sessão 25/08).
- **Offscreen `capturePage` sai preto** pra páginas com JPG escuro — validar por DOM (`img.complete && naturalWidth>0`) e screenshot visual no browser real.
- **Locale em app com locale raiz + módulo**: chaves `settings.*` vivem em `src/modules/settings/locales/`, nunca no locale raiz (teste de paridade quebra).
- **Receiver browser PC vs TV**: browser funciona sempre (fetch liberado); TV empacotada é o caso difícil — testar IP manual + tecla vermelha.
- **A palco-bridge deve subir no BOOT do app** (`App.vue` onMounted, dinamicamente, fora da janela de projeção) — NÃO no mount do PalcoCard. Se subir só no card, hino/bíblia/timer não espelham a menos que o operador tenha visitado Configurações → Projeção antes. Sintoma: "sender on, receivers conectados, TV no idle".
- **Dynamic import de `workspace.mjs` falha silenciosamente dentro do slot** (arrasta basic-ftp/electron-net/crypto) — `servePath('local://...')` devolvia null e o catch engolia. Importar `./paths.mjs` (só `resolveMediaDirectory`) em vez do workspace inteiro.
- **resolveBgUrl NUNCA faz fallback `${base}${bg}`** pra caminho não-resolúvel — vira `http://ip:7080/local://...` = 404 na TV. Se serveLocal falhar, mandar SEM background (a TV usa bg-fallback dela). Capas/slides de hino (`local://media/images/...`) resolvem via servePath → `/media/`.
- **Replace/regex em HTML de receiver pode COMER tags de fechamento** — o replace do splash engoliu o `</div>`: todo o body (idle incluído) virou filho do splash e era removido junto após 2.5s → tela preta sem idle nem versão. Após qualquer replace em HTML, validar estrutura (splash fechado ANTES do `<script>`, sintaxe dos scripts com `new Function`).
- **`pkill -9` durante `vite build` corrompe o dist** — app abre com janela fantasma (`ERR_FILE_NOT_FOUND /assets/*.js`) e o CDP HTTP conecta mas não responde (DevTools pendurado no renderer sem página). Sintoma diagnóstico: `curl 127.0.0.1:9223/json/version` conecta e dá timeout. Fix: `rm -rf dist && vite build` limpo antes de reabrir. Sempre build completo → conferir `dist/index.html` existe → só então abrir o Electron.
- **Splash screen do receiver usa JPG** (`splash-palco.jpg`, arte oficial 1920x1080, `object-fit:contain` sobre `#0A0E1A`), não SVG inline (quebrava em TVs). Some no WS OPEN ou 2.5s.
- **UI: NUNCA early-return numa lista de destinos MISTOS antes de processar todas as fontes** — `renderMonitorList` fazia `if (!extended.length) return` antes do bloco de TVs do Palco: sem monitores físicos (notebook + TVs wireless), as TVs nunca apareciam. Montar sempre (monitores → TVs → "Nenhuma tela" só se vazio de fato).
- **UI condicional: seletor "Destino do palco" (`PalcoRouteSelect`) só aparece com o sender ATIVO** — usuário: "só faz sentido aparecer quando a funcionalidade estiver ativa". O componente faz poll do `status().running` (4s) e se esconde com o Palco desligado. Mesmo princípio vale pra qualquer controle de cast: nada de UI morta com a feature off.
- **Contador "N TVs conectadas" = conexões WS, não dispositivos** — 3 abas do browser no mesmo PC = 3 "TVs". Não deduplicar por IP (2 receivers legítimos podem vir do mesmo host em teste); se o usuário estranhar, explicar que cada aba/receiver é uma conexão.
- **`pkill` com string que casa o PRÓPRIO comando se mata** (`pkill -9 -f louvorja-piano` num comando que contém essa string → SIGTERM no shell). Separar kill e build/open em chamadas distintas OU usar padrão que não autologue (`electron/dist/electron`).
- **`cmd | tail -1 && next` engole exit code** — o pipe retorna o exit do `tail` (0), então o Electron abre mesmo com `vite build` FALHO → `ERR_FILE_NOT_FOUND` fantasma. Redirecionar pro log (`> /tmp/build.log 2>&1`) e checar `dist/index.html` ANTES de abrir o app.
- **Multi-TV: receiver aceita só IP na entrada manual** (conecta na porta padrão do slot 0). Pra TV 2+ falta aceitar `IP:PORTA` (ex.: `192.168.1.192:7083`) — pendência conhecida.
- **Áudio em loop na TV = receiver recarregando src a cada sync**: `a.src=url` incondicional no `case 'audio'` + bridge mandando `play+url+positionMs` a cada 3s reiniciava do zero em ciclo. Receiver: src só troca se a URL mudou, `play` em tocando é no-op, `seek` só corrige desvio >0.3s e retoma play se pausado com target>0.2. Bridge: sync periódico manda `action:'seek'`, NUNCA `play` com url. Idempotência é requisito de TODO handler do receiver.
- **Rota `tv`: o áudio local é o CLOCK das letras, não a caixa de som**: slides/fila avançam por `audio.timeupdate`. Não pausar o `<audio>` local ao enviar áudio à TV; manter `volume=0` e `play()` local para a timeline avançar, enquanto a TV é a única saída audível. `pause()` pausa local + envia `audio.pause`; `play()` retoma os dois. Ao trocar PC→TV na mesma faixa, tratar `routeChanged` como envio inicial de play. Pausar localmente sem clock produz áudio da TV adiantado e letra atrasada/congelada.
- **MP3 de liturgia pelo popup é caso especial até o sender ser corrigido**: o popup legado pode emitir `video` com URL `.mp3`, depois `audio.stop`, e seeks nos dois canais. Receiver deve detectar `isAudioUrl`, esconder/limpar `#video`, alimentar o único `<audio id="audio">`, mostrar now-playing/EQ/bg e tocar também em replay/load sem `action:'play'`; proteger esse áudio do `audio.stop` dual. Antes de culpar a TV, WS spy deve registrar mensagem bruta e browser headless deve conferir `#np`, título, `audio.paused/currentTime` e `src`.
- **Rodapé de versão precisa ser overlay independente do idle**: fora de `#idle`, z-index alto, safe-area LG (`right/bottom >=3vh`), alto contraste e texto estático no HTML. JS só aprimora; não depender de `fetch(appinfo.json)` em `file://` webOS. HTML do receiver servido pelo sender: `Cache-Control: no-store`; main mudou = restart Electron; TV mudou = IPK + relaunch.
- **Rota de áudio é escolha prévia em Configurações → Projeção → Palco**, persistida: `pc` = só PC (Palco recebe visual, `audio.stop`); `tv` = PC pausa e TV toca; `both` = PC+TV sincronizados. Não confundir `pc` com `both`, e nunca deixar essa escolha afetar projeção HDMI/cabo.
- **Rota TV = caixa E letra JUNTAS (nunca bloquear a projeção de letra na rota tv)** — o receiver decodifica áudio independente do visual `projection`. Racional de domínio (usuário): ambiente HÍBRIDO (PC+cabo) → som vai pras caixas do PC, rota "só TV" não faz sentido; ambiente SÓ-TV (sem som) → TV é a saída E mostra a letra. `play()` do media store na rota tv: volume 0 local (senão fade-in faz PC ecoar junto).
- **Seek NUNCA vai ao receiver pausado (rota tv)** — o handler `seek` do receiver tem auto-play (`a.paused&&target>0.2→playWithFallback`, design p/ modo Ambos). Watcher de `currentTimeSec` deve IGNORAR rota tv; syncAudio rota tv só manda seek durante play (throttle 3s, desvio >2s). Pausa no PC propaga via `lastTvPlaying` (play→reenvia faixa+posição, pause→`action:'pause'`, sem sessão→`stop`→idle).
- **Hinos preservam o asset próprio por padrão**: `hymns.overrideBg=false` usa capa/slide da música; opt-in `true` deixa o background configurado no escopo `hymns` vencer para todas as músicas. Nunca transformar em preferência global.
- **Caixa de letra = PADRÃO FOLHA, caixa JUSTA — em TODOS os destinos (receiver, preview E views via cabo)**: `border-radius: clamp(14px,2.4vmin,32px) 0 clamp(14px,2.4vmin,32px) 0` (2 cantos opostos, NUNCA 4), borda fina `clamp(2px,.2vmin,4px)`, sombra `0 10px 30px rgba(0,0,0,.4)`. **A caixa deve ENCOLHER ATÉ O TEXTO em TODOS os browsers — `display:table; margin:0 auto; max-width:86vw` (fix 3e92093) — NUNCA `width:84vw` fixo NEM `width:fit-content`** (erro real 26/08 #1: caixa sempre com 84% da tela e texto flutuando dentro parecia "padding exagerado" mesmo com padding já mínimo 1.8vmin lateral / 1.6vmin vertical; o culpado era a largura, não o padding. Erro real #2: `fit-content` em `position:absolute` COLAPSAVA no Chromium antigo do webOS/simulador — texto do versículo sumia, só o rodapé ficava; funcionava no Chrome atual do PC, quebrava só na TV. `display:table` = shrink-to-fit universal desde sempre). Estrutura: `position:absolute; top:50%; left:0; right:0; transform:translateY(-50%); display:table; margin:0 auto; max-width:86vw; max-height:72vh`. Padding MÍNIMO: `1.6vmin 1.8vmin` (usuário: "mais próxima ao texto com o mínimo de padding"). Letra do receiver: **branca, bold 700, CAIXA ALTA (text-transform:uppercase), letter-spacing .03em** (padrão do player, pedido explícito). Classes `box-on`/`box-off` mutuamente exclusivas no handler (remove a oposta antes de add). Borda AJUSTÁVEL na personalização: `boxBorderOpacity` (0.1–1, def 0.25) + `boxBorderWidth` (1–8px@1920, def 2), serializados `boxBorderOp`/`boxBorderW`. Nas VIEWS DE PROJEÇÃO via cabo: hinos mantêm caixa justa; Bíblia é exceção deliberada para leitura à distância — `BibleProjectionView` usa caixa horizontal `width:100%`, `box-sizing:border-box`, `max-width:min(92rem, 92%)`, reduzindo quebras sem encostar no limite seguro da stage.
- **Capa de música (isCover) = AMARELA #f6c32a, weight 900, SEM caixinha** (paridade `media-projection__title--cover` do cabo): `useMediaStore` já expõe `isCover` no runtime → `palco-bridge` repassa → `palco-session` envia `isCover` na mensagem `projection` → receiver aplica classe `cover-on` (amarelo, w900, uppercase, background none/padding 0/border none). Letra (não-capa) segue com caixinha branca. `cover-on` entra no reset/idle remove-list junto com box-on/shadow-on.
- **WS de client NÃO recebe broadcast de outro client** — o sender não re-transmite. Pra testar como a bridge faz: `palco.send` via CDP. E `palco:send` deve normalizar string JSON (spread de string vira `{0:'{',...}` e entra no replay).
- **CDP: filtrar page por URL** (`x.url.includes('dist/index.html')`) — senão pega a janela DevTools (`devtools://`) e `window.louvorja` é undefined.
- **Receiver embutido lê do disco a cada request** — mudou `electron/palco/receiver.html`? Sem rebuild do Vite o main novo já serve (mas renderer da bridge ainda precisa de rebuild). TVs com página ANTIGA em memória não revalidam: mudança no receiver SEMPRE exige reload/reabrir na TV (fechar e abrir o app da TV resolve).
- **Mudanças no MAIN process exigem restart do Electron** — reload do renderer (CDP `location.reload()`) não recarrega .mjs do main. Sintoma: feature nova no main "não existe" até reiniciar. ANTES de debugar "feature nova não funciona", conferir a IDADE do processo (`ps aux`): app aberto antes do código = código não está nele. Restart pede consentimento; popups de control-bar restaurados ficam com HTML antigo (recarregar via CDP `Page.reload`).
- **Vídeo ARQUIVO local nas TVs = protocolo `video` NATIVO (nunca frames)**: detecta pelo URL do source (`file:...local-video-player?src=local://app/<path>`), resolve path (win32 slice `/C:/`), `servePath` publica em cada slot, envia `{type:'video',url,action:'play'}` 1x por arquivo. **Cache pelo PATH original, nunca pela URL retornada por `servePath`**: ela contém timestamp novo a cada chamada; comparar URL causava `play` a cada tick e reiniciava o vídeo infinitamente. A cada poll, ler somente `video.paused` na fonte e mandar `pause`/`play` à TV APENAS na transição de estado; NUNCA sync periódico de seek. Fullscreen real + `ended`→`showIdle` automático. **`#video` precisa `z-index:20` (`#idle` usa 10)**: idle não pode sobrepor mídia local durante play; no `onended`/`stop`, ocultar vídeo e então chamar `showIdle`. `stopPalcoSlideSync` manda `video stop` a todos os slots no close.
- **YouTube em receiver webOS NÃO usar `<iframe>` sem teste no simulador real**: tentativa de `youtube` + iframe embed quebrou o runtime do app webOS (erro JS e receiver não abria), apesar de passar `node --check`. Rollback obrigatório antes de seguir. Não assumir compatibilidade por Chrome/Node. Para streaming fluido, usar player/plataforma webOS comprovadamente compatível (ou app/SDK nativo), com teste no simulador e aparelho antes de substituir fallback. Captura de frames é visualmente inviável para vídeo contínuo; nunca declarar como solução final.
- **Destino padrão de recurso externo = TODAS as telas**: todos monitores/projetores estendidos **e** todas TVs conectadas. Lista vazia significa “todas”, não “nenhuma”; só uma seleção explícita substitui esse default. No painel misto, TVs devem nascer marcadas quando `palcoSelected=[]`; ao desmarcar uma, materializar IDs das demais como seleção explícita. `resolveTargetMonitorIds`: `configured.length > 0 ? configured : allExtended`.
- **Frames de vídeo YouTube/site: NOME ÚNICO por envio (cache de URL!)** — `frame.png` fixo = browser do receiver cacheia e a TV nunca revalida ("vídeo só muda no F5"). `frame-<ts>.png`. **Véu escuro do receiver só com texto**: `projection` com `m.text` vazio → `$('veil').style.display='none'` (senão frame fica 45% mais escuro). **LRU no `serveMediaBase64`** (24 itens) — nomes únicos cresceriam sem limite. Qualidade: JPEG q82 (3-5x menor que PNG), intervalo 300ms, capturar do MIRROR fullscreen (`mirrorWindows.find(!destroyed)`) em vez do popup pequeno.
- **Replay de estado (`lastByType`) devolve conteúdo MORTO a quem reconecta** — o slot cacheia a última msg POR TIPO; se a última `projection` foi um frame de vídeo capturado, TODO receiver que reconecta (app da TV reaberto) recebe `idle → bgPalco → projection(frame.png)` e fica "preso no vídeo pausado" (frame estático vence por vir depois). Fix: `slot.clearProjectionReplay()` (delete `projection` do cache + broadcast idle) no encerramento da projeção externa, junto do `video stop`. Regra geral: estado de replay tem que representar o estado VIVO — qualquer "projeção sintética" (frames) precisa ser descartada quando a fonte fecha.
- **`vite build` com paths absolutos NUNCA via `npm run build -- --base=./`** (npm fica com a flag: "Unknown cli config"; Vite builda absoluto e popups NOVOS abrem brancos/"carregando" sem erro, janela principal antiga sobrevive). Sempre `node_modules/.bin/vite build --base=./` ou `npm run electron:preview`.
- **`startPalcoSlideSync` parte do `openWebProjectionWindows` (logo após set do `currentProjectionMode`), NÃO só de did-finish-load** — janela restaurada pela sessão não re-dispara o evento de load depois que o modo já está setado (sintoma: YouTube aberto, sender on, TVs no idle, replay sem frames). did-finish-load fica como reforço.
- **Antes de debugar "TV não recebe nada": conferir o Palco SUBIU** — o sender é toggle manual e NÃO restaura em todo boot (`curl :7080/status` → clients:0 e porta 7081 recusada = Palco desligado; ligar em Configurações → Projeção). Restart do app pode derrubar o estado.
- **Frame externo: validar contadores no MAIN antes de culpar TV** — expor `{mode,source,timer,ticks,sent,error}`. `ticks>0 + sent=0` significa erro de captura/serialização no sender; exemplo real: `NativeImage.toJPEG()` retorna `Buffer`, então usar `toJPEG(q).toString('base64')`, NUNCA `.toDataURL()`.
- **Electron pode deixar DOIS processos principais vivos** — matar apenas wrapper Node não basta. Sintoma: preload novo oferece IPC, mas main responde `No handler registered`; CDP/Palco podem pertencer ao processo velho. Encerrar todos `electron/dist/electron --class=louvorja-piano` sem `--type=`, conferir 0, subir UMA instância. Não usar `pkill -f` que casa o próprio shell.
- **Janela restaurada pela sessão pode ter preload/control-bar antigo e fonte órfã** — recarregar control-bar para atualizar preload; adotar a janela player pelo URL no main ou oferecer `ensurePalcoProjectionSync()` IPC. O sync deve nascer explicitamente quando control-bar fica pronta; não confiar em `did-finish-load` da restauração.
- **Após patch em control-bar HTML, validar JS extraído com `node --check`** — uma aspa extra derruba player inteiro (play/pause/seek/autoclose/painel). Cabo: wrapper flex column `gap:4vmin` agrupando caixa+referência (`BibleProjectionView.__stage-inner`). Receiver: `#footer` movido pra dentro do `#content` + classe `body.proj-ref-below` (toggle por `Boolean(m.footerRef)`) reorganiza em coluna centrada — sem `footerRef` (hinos) layout original intacto.

## Pitfalls da rodada híbrida 26/08 (tarde — PRs #121/#3, IPK 0.1.37)

- **Replay do palco-server NÃO pode gravar transientes**: `pause/play/seek` → `broadcastTransient()` (só conectados), NUNCA em `lastByType`. Sintoma: quem conecta depois recebe `timer` velho + `video play` sem URL (receiver mostra contador, não toca). **EXCEÇÃO (fix 135b71d, 27/08): `audio stop` AGORA GRAVA replay** — como transient, o cache ficava com o `play` velho e o F5/tecla azul RESSUSCITAVA o MP3 parado; stop é estado terminal válido.
- **HTTP Range no `/media/` é obrigatório** (206 Partial Content) — sem isso o `<video>` baixa o MP4 inteiro antes de tocar (stutter/delay).
- **Autoplay browser: fallback mudo** — `play()` NotAllowedError → retry `muted=true` + badge "toque p/ som" → 1º clique desmuta. Válido p/ vídeo E áudio (o case `video` original não tinha o fallback que o áudio já usava). IPK/webOS toca com som direto.
- **Pause/play/stop do popup vão nos DOIS canais** (`video` E `audio`) — MP3 de liturgia pode estar tocando na TV enquanto o operador usa o popup do vídeo.
- **Controle REAL do PPT é `pdf-control-bar.html`** (PPTX → LibreOffice → PDF → main abre player PDF). `ppt-control-bar.html` existia fora do fluxo. Sincronizar os DOIS sempre.
- **Captura de slide PDF.js**: `capturePage()` pega frame cinza (loading/GPU). Usar `canvas.toDataURL()` do player, ACHATADO em canvas opaco branco — alpha/premultiplicação compõe contra preto no WAM e escurece azul/amarelo vs operador.
- **URL de mídia por slide ÚNICA** (`ppt-slide-<ts>-<slot>.png`) — nome fixo = cache stale, navegação não atualiza a TV.
- **Receiver `file://`**: `fetch('appinfo.json')` bloqueado → versão default EMBUTIDA no HTML (5º ponto de sync); `location.hostname` vazio → scan usa sub-rede do `palcoHost` salvo antes do default `192.168.1.100`.
- **Porta: UI mostra HTTP; WS = HTTP+1**. Entrada "só porta" tenta a porta como HTTP E como WS (digitou 7082 → WS 7083). `localStorage.palcoPort` persiste a escolha do operador (multi-TV estável).
- **tvBroadcast atualiza `palco.slots()` antes de CADA envio** — receiver conectado depois do boot do popup ficava fora da lista (pause nunca chegava).
- **Áudio sem metadados**: now-playing extrai nome do arquivo da URL (decodeURIComponent, sem extensão) — nunca fundo preto.
- **`closeWebProjectionWindows` manda `video stop` E `audio stop`** via `broadcastAll` — MP3 ficava preso no now-playing após fechar popup.
